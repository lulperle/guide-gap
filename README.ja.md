# guide-gap

[English](README.md) | **日本語**

問い合わせチケットのバッチとドキュメントを読んで、チケット1件ごとに1つの問いに答える:
**ページが無いのか、それともページはあって誰も見つけられなかったのか。**

この2つはチケットのキュー上では見分けがつかないのに、直し方も担当者も違う。

```
content gap      -> 誰かがページを書かないといけない
findability gap  -> ページはある。タイトル、検索語、あるいは
                    ユーザーが実際にいた場所からの相互リンクが悪い
not deflectable  -> どんなドキュメントでもこのチケットは防げなかった
```

最初の2つを混同すると、取り得る中で最悪の結果になる: ドキュメントが既にカバーしている領域に新しいページが増え、ドキュメントは大きくなり検索しづらくなり、**その結果、チケットの原因になったことがより下手になる**。新規ページの本数は進捗ではない。3番目のバケツも同じくらい重要で、アクセス権申請や不具合をドキュメントの失敗として数えると自己解決率の目標に到達不可能になり、誰も届かない目標は使われなくなる。

AWS 上に構築: boto3 経由の Bedrock（検索は Titan Text Embeddings V2、yes/no 判定と下書きは Converse API 経由の Claude Sonnet 5）。エージェントフレームワークは使っていない — これはバッチに対する定期的な1パスであり、2つのチケットを**なぜ**同じグループにしたのか示せないエージェントは、ここでは示せる算術より悪い。

## 動かす

```bash
python -m venv .venv && make install
make test                    # 84 tests、認証情報なし、約5秒
make analyse                 # Bedrock に対して1パス、out/drafts/ に書き出す
make eval                    # 3回繰り返し、ラベルに対して採点
make eval-baseline           # 類似度閾値のベースライン、モデル呼び出しなし
```

`AWS_REGION` の既定は `us-west-2`。以下の測定はすべて検証用アカウントに対して実行したもので、実行ごとの artifact は `evals/` 以下に commit してあるので、ここの数字はどれも呼び出しを1回も使わずに再計算できる。

## やっていること（順番どおり）

```
各ページの各セクションを embedding する （ページ単位ではない — 後述）
  -> チケットごとにコサイン類似度で候補箇所を絞る
  -> 箇所ごとに問う: これでユーザーは次に何をすべきか決められるか？
  -> content gap / findability gap / not deflectable
  -> content gap だけをクラスタリングする（「1ページで両方に足りるか？」と問う形で）
  -> 複数人が聞いてきたクラスタだけ下書きを書く
```

全部クラスタリングして大きいグループから下書きを書くのが素直な形だが、それは間違っている。問い合わせキューで最大のグループは、たいていドキュメントが既に答えている質問である — **だからこそ最大のグループになっている**。なので生の件数から下書きを書くと、MFA についての2枚目のページができて、本当の穴は手つかずで残る。

## 測った結果

22チケット、7ページ、32セクション。ラベルは全部、どのモデルも動かす**前に**手で書いた。採点はそのラベルに対する厳密な文字列比較である。このリポジトリのどこでも、モデルが別のモデルの出力を採点していない。

2方向の誤りは別々に数える。同じ悪さではないから:

- **wasteful（無駄）** — ドキュメントが既に答えているのに「ページを書け」と言った。レビュアーが重複に気づいて下書きを却下する。
- **costly（高くつく）** — 何も書かれていないのに「ドキュメントがカバーしている」と言った。穴はレポートから消えて、誰も見直さない。

| バージョン | 正解率 | wasteful | costly | 提案ページ数 |
|---|---|---|---|---|
| 類似度閾値のみ（ベースライン） | 17/22 (77%)、3/3実行が同一 | 5 | 0 | 2 |
| entailment、箇所が空で届いていた | 14/22 (64%) | 5 | 1 | 0 |
| entailment、`maxTokens=8` | 19/22 (86%) | 2 | 1 | 0 |
| **entailment、`maxTokens=256`** | **平均 20.7/22（91〜95%）、3回** | 1〜2 | **3回すべてで 0** | 2 |

実行ごとの生データ: [`evals/results.json`](evals/results.json)（entailment）と [`evals/results-threshold.json`](evals/results-threshold.json)（ベースライン）。

真ん中の2行は意図的にこの表に入れてある。一方はベースラインより悪く、どちらも**自信があって安定していてもっともらしい出力**を生むバグが原因だった。それは隠す価値のある失敗ではなく、記録する価値のある失敗の仕方である。

### あの表の裏にある3つの発見

**類似度ではカバレッジを判定できない。** チケットごとの最良セクションのスコアを実測すると、ドキュメントが答えているチケットは 0.241〜0.595、答えていないものは 0.205〜0.370 に入る。答えられている3件が「答えられていない側」の範囲の内側に座るので、0.370 より上に線を引けば t04・t07・t10 を誤分類し、0.241 より下に引けば t11・t14・t17 を誤分類する。**どこにも分離する閾値は無く**、調整しても間違えるケースが入れ替わるだけである。類似度が測っているのは話題の近さで、「答えがこの中にあるか」は entailment である。請求についてのページは、これまで聞かれた全ての請求関連の質問と話題的に近い — そのページが何も言っていない質問も含めて。なので類似度は候補の絞り込みに格下げして、yes/no 判定が決めるようにした。しかも2回: カバレッジについて1回、2つのチケットが1ページにまとまるかについて1回。`COVERED = 0.45` はベースラインとしてだけ残してあり、しかも**この22チケットに合わせて当てはめた値**である — それが caveat ではなく発見のほうである。

**ページではなくセクション。** ページ全体を embedding すると、そのページが答えていたかどうかに関係なく全チケットが 0.17〜0.61 の帯に入る。400語の手順ページと2文の質問は主に長さと文体で違っていて、それがコサインを支配してしまう。セクション単位の max は本当に効く問いを立てている — **ここに答えている箇所があるか**。関連して、カバレッジの候補リストは1ページ1件に**重複排除してはいけない**。それをやるとページ内の最高スコアのセクションしか検討されないので、**別の**セクションが答えているチケットが「書かれていないページ」として報告される。この1つの間違いが、最初の entailment 実行の8件の誤りのうち4件を生んでいた。

**返答の切り詰めはエラーにならない。** `maxTokens=8` は安い正しさの検査に見えた — 答えは1語なので。しかし Claude Sonnet 5 はテキストの前に `reasoningContent` ブロックを出し、そのブロックも `maxTokens` に課金される。結果、呼び出しは HTTP 200 と整った形のメッセージを返し、**テキストブロックが1つも無い**状態になった。空文字は「いいえ」として parse されたので、切り詰められた呼び出しは全部「自信のある否定」になった — しかも3回の繰り返しを通して安定して。まさにそれが本物の判断のように見えた理由である。64トークンでも64呼び出しのうち8件がまだ切り詰められた。観測される reasoning の長さは160トークン前後なので、上限は今 256 にしてある。`Usage.truncated` が `stopReason == "max_tokens"` を数え、eval がそれを表示するので、これが黙って再発することはない。reasoning を完全に切る（`thinking: disabled`）のも動いて、6トークンで答えが返る — そして判定が測定できるレベルで悪くなるので、その安い道は利用可能だが採っていない。

小さいものが2つ。どちらも始める前に知っておく価値がある:

- **`temperature` は端的に拒否される** — Sonnet 5 は `ValidationException: temperature is deprecated for this model` を返す。再現性のための定番のレバー `temperature=0` が存在しないので、eval は出力が固定されていると仮定するのではなく、実行を繰り返して安定性を測っている。上の 91〜95% が単一の数字ではなく範囲なのも同じ理由である。
- **空の箇所には、まったく理にかなった「いいえ」が返る。** `build_index` が箇所のテキストを入れ忘れていたとき、バッチは完走し、全チケットを content gap として報告し、エラー0件を記録して、**発見のように見えた**。今は `entail.answers()` が空の箇所について問う前に raise する。

### 人が読む形に描画して見つかった2件

どちらもテストが全部緑のまま生き延びていて、どちらもこれらの提案のレビュー画面 [guide-review](https://github.com/lulperle/guide-review) を作っている最中に捕まった。**機械の出力についての数字を信じる前に、その出力を読者の前に置け**という主張の根拠である。

- **`Draft.open_questions` が折り返された項目を全部切り詰めていた。** 箇条書き記号で**始まる**行だけを残していて、下書きは全角40文字くらいで折り返されるので、但し書きが「命名規則があるのかどうかは、」で終わってその後が無い状態で届いていた。気づかれなかったのは、このプロパティが**件数**として使われていて、件数は正しかったから — 下書きごとの未解決の問いの数、つまりこのプロジェクトが「下書き工程は安全である」の証拠として報告している数字は正しく、問いそのものは半分に切れていた。最初の修正は継続行がインデントされていることを要求したが、次の実行は行頭に揃えて折り返して再び壊した。なのでルールは今、CommonMark の lazy continuation（空行で項目を閉じる）である。
- **下書きのタイトルがリテラル文字列「タイトル」として出てきた。** 原因は下書きプロンプトで、出力テンプレートに `# タイトル` が「見出しは書かれているとおりに使え」という指示の下に置かれていた。モデルはまさにそのとおりにやって、本当のタイトルを次の行に置いた。`well_formed` は `True` を返した — 必要な3つの見出しは揃っていて、タイトルは一度も検査されていなかったので。プロンプトと検査の両方を直した（`PLACEHOLDER_TITLES` 参照）。プレースホルダのタイトルは、ここでプロンプトのずれが取る具体的な形であり、`well_formed` はずれを捕まえるために存在しているのであって、ずれが止まったと仮定するために存在しているのではない。

### まだ直っていないこと

- **t08 は毎回失敗する。** これは判断のミスではなく検索のミスである: `account-request` の「年度末の払い出し期間」を扱っているセクションが top-5 の候補に一度も入らないので、yes/no 判定がそれを見ることがない。一致は語彙的には明白（年度末、営業日）で、dense のみの検索がそれを取り落とす — 直し方は lexical と dense のハイブリッドで、ここには実装していない。
- **t10 は実行間で結果が入れ替わる**し、クラスタリングもそうである: t14/t15/t16 は1回目の実行では3件1クラスタになり、2回目と3回目では 2+1 に分かれた。同じ入力、同じコードで。temperature の制御が無い以上、これが単一実行の安定性の下限であり、上のどの数字にも繰り返し回数を添えている理由である。
- **fixture は作り物。** `fixtures/tickets.yaml` は、ガバメントクラウドのヘルプデスクのキューに似せて私が書いた22チケットである。パイプラインは本物で測定も本物だが、それらは「そういうキューはこう見えるだろう」という私自身の想像に対する測定である。実物のチケット文面なら数字は変わるだろうし、おそらく上には変わらない。
- **ペア確認は O(ペア数)** で、ペア数はバッチサイズの2乗である。22チケット（9呼び出し）では問題なく、数百件でも扱えるが、数千件のバッチには blocking か、もっと安い1次通過が必要になる。ここでは解いていない。

## 1パスのコスト

推定ではなく5パスの実測: カバレッジ判定55〜63回、ペア判定8〜10回、下書き2本、入力約41〜47kトークン、出力1.6〜4.6kトークン、148〜165秒。出力のばらつきは「確認が必要な点」である — 下書きが各6件を認める実行は、3件を認める実行のおよそ2倍かかる。そのコストの向き方としてはそれが正しい。embedding は `.cache/embeddings.json` にキャッシュされるので、パイプラインの決定的な半分は無料で再実行でき、判断の呼び出しだけが課金される。

## 構成

```
guide_gap/
  bedrock.py    AWS と話す唯一のファイル
  corpus.py     ページとチケットの読み込み、ページをセクションに分割
  retrieve.py   セクションに対するコサイン検索。純粋な算術、ネットワークなし
  entail.py     2つの yes/no プロンプト、そしてトークン予算の教訓
  coverage.py   3分岐の判定と、検査を行う順序
  cluster.py    確認済みペアに対する single-link union-find
  draft.py      下書き。知らないことを列挙することを要求される
  metrics.py    レポート。分母を両方見せる
  score.py      ラベルに対する決定的な採点
  pipeline.py   1パス。上をつないでいる
corpus/guide/   YAML front matter 付きの markdown 7ページ
fixtures/       ラベル付きの22チケット
evals/          繰り返しハーネスと、commit された生出力
infra/          CDK スタック — synth して assert するだけ、デプロイはしない
docs/           生成された下書き1本を無編集で、証拠として
```

`bedrock.py` より上は全部、ベクトルとテキストに対する純関数である。だからテストスイートは認証情報を1つも持たずに CI で走る。

## 主張していないこと

- CDK スタックは**一度もデプロイしていない**。synth は通り、`tests/test_infra.py` がテンプレートに対して assert する。どのアカウントにもリソースは存在しない。実際のデプロイに何が足りないかは [`infra/README.ja.md`](infra/README.ja.md) 参照（インターフェースエンドポイント付きの VPC、カスタマー管理キー、チケットのエクスポート連携）。
- 自己解決率の改善は主張していない。これは**穴がどこにあるか**を測って候補ページを下書きするもので、それを公開したらチケットが減るかは、実物のドキュメントと実物のトラフィックに対する前後比較であり、それはやっていない。
- 生成された下書きは未レビューの機械出力である。1本を [`docs/example-draft.md`](docs/example-draft.md) に commit してあるのは、下書きプロンプトが**知らないこと**に対して何をするかを示すためにほかならない: タグの命名規則が分からないとき、それを捏造せずに「確認が必要な点」の下に列挙する。それがこの工程を自動化しても安全である理由の性質であり、`Draft.well_formed` はその見出しが無い下書きを失敗させる。`evals/export_review.py` は1パスをレビュー用の bundle として書き出す — すべての判定を、それが下された箇所と一緒に — 宛先は [guide-review](https://github.com/lulperle/guide-review) で、そこで人が受理・却下する。
