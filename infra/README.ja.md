# infra

[English](README.md) | **日本語**

分析を週次で走らせるための CDK スタック。**一度もデプロイしていない。** synth は通り、`tests/test_infra.py` が生成されたテンプレートに対して assert するが、どのアカウントにもリソースは存在せず、このリポジトリのどの数字もこれを AWS で動かして得たものではない。トップレベルの README にある測定結果は、`scripts/analyse.py` と `evals/run.py` をローカルから Bedrock に対して走らせたものである。

```
make layer            # Lambda ランタイム用のレイヤをビルドする。このラップトップ用ではない
make synth            # テンプレートだけ。認証情報は要らない
.venv/bin/python -m pytest tests/test_infra.py
```

## 形

```
EventBridge (週次、月曜 02:00 UTC)
  -> Lambda  guide_gap.pipeline.analyse
       読む   s3://…/guide/*.md, s3://…/input/tickets.yaml, s3://…/cache/
       書く   s3://…/runs/<stamp>/report.txt, drafts/*.md, result.json
  -> CloudWatch アラーム -> SNS トピック（コード中に subscription は無い）
```

## 反論する価値のある判断

**下書きは S3 で止まる。** ここからドキュメントに書き込むものは無い。生成されたページが人に読まれないまま利用者に届くことは、下書きプロンプトが避けるために作られている失敗そのものであり、自動 commit はその IAM 権限を1つ手放すことになる。

**Lambda。ただし天井を書いておく。** 1パスは逐次の Bedrock 呼び出しで、22チケットに対して約66回、実測3分。今日は収まる。数千チケットでは収まらない — Lambda は15分で止まるからである。`MAX_TICKETS_PER_RUN` がそれを、驚きのタイムアウトではなく明示的な入力にしている。実行時間のアラームは10分のタイムアウトに対して8分で鳴るので、障害になる前に警告がある。移行するときの行き先は Fargate。

**バケットはスタック削除時に保持する。** 受理された下書きは誰かが編集したドキュメントであり、それ以外のここのリソースはすべて `guide_gap_stack.py` から再構築できる。

**Bedrock の権限はリージョンごとに、意図的に列挙している。** `us.anthropic.claude-sonnet-5` はクロスリージョンの推論プロファイルである。呼び出しはプロファイル ARN に対して行うが、Bedrock はその後ルーティング先のリージョンで基盤モデルを呼び、その呼び出しは同じ identity に対して認可される。プロファイル ARN だけを許可すると、呼び出しによって `AccessDenied` が出たり出なかったりする — それはポリシーのエラーではなくスロットリングや不安定なエンドポイントのように読める。なのでポリシーは、プロファイルがルーティングし得る全リージョンの基盤モデル ARN を列挙していて、`test_infra.py::test_the_inference_profile_is_permitted_in_every_region_it_routes_to` が1つ落ちたら失敗する。

**SNS の subscription はコードに入れない。** 誰が呼ばれるかはチームの判断であり、ここにメールアドレスを書けば公開リポジトリに commit することになる。

## 足りていないもの

- 一度もデプロイしていないので、実際の IAM 評価にも、実際のコールドスタートにも、実際の S3 イベントにも検証されていない。証拠ではなく設計として読むもの。
- **VPC が無い。** 関数は Bedrock と S3 とだけ、パブリックエンドポイント経由で話す。ガバメントクラウドの文脈ではこれは誤った答えで、両方へのインターフェースエンドポイントを持つ VPC と、サブネットおよびセキュリティグループの配線が必要になる。
- **KMS の CMK が無い。** ここでは既定の `S3_MANAGED` 暗号化である。監査対象の環境が求めるのは、ローテーションポリシー付きのカスタマー管理キーである。
- チケットのエクスポートは、このスタックの外の何らかの手段で `input/tickets.yaml` に着地する。それを配線するところが実際のデプロイの出発点であり、その形は上流がどのチケットシステムかに完全に依存する。
